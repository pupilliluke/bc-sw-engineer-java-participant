1, PERMANENT 503 FROM WIREMOCK

  stub 503, repeated calls to find()

  breaker CLOSED -> OPEN after 5 calls, every response available=false

Observed but not as the GUIDE describes it. The row says retries then OPEN, and
there were no retries. Five calls to find() produced five HTTP requests and five
breaker records, not fifteen. @Retry is configured with maxAttempts 3 and it
never fired.

The cause is the annotation composition. fallbackMethod is on @CircuitBreaker,
so a failure is converted into a successful return, and @Retry as the outer
aspect sees success and has nothing to retry. The retry config is correct and
inert. Moving fallbackMethod to @Retry would restore retries at the cost of the
breaker no longer seeing per-attempt outcomes. Left as the GUIDE writes it and
documented in docs/resilience-notes.md.

4, RETRY A NON-IDEMPOTENT WRITE

  Thought experiment, deliberately not demonstrated.

A retried write is not safe because a call that times out may still have
succeeded on the server. The CRM cannot distinguish no answer from a lost
answer, so retrying a create produces a second customer, one per attempt. This
is the same argument as the consumer side in lab 31, where a redelivered event
would run the side effect twice and eventId is what makes it safe. There is no
equivalent key on an HTTP create unless the caller supplies an idempotency key,
so retry stays on reads.

Not demonstrated because demonstrating it means writing a knowingly unsafe
endpoint, so the policy is documented instead.
