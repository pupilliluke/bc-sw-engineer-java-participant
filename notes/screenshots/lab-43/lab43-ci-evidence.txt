=== What had to change before this passed ===

Two problems, both from the starter assuming a different CRM.

1. Paths. The starter sets working-directory and cache-dependency-path to
   examples/lab43-crm. This project's pom is at examples/lab43-crm/crm-api,
   because lab41-crm is a project folder containing the Maven module alongside
   compose.yaml and ddl/. Four settings corrected.

2. JWT_SECRET. application.yml declares northstar.security.jwt-secret with no
   default. Locally it arrives via spring.config.import from .env, which is
   gitignored and therefore absent on a runner. The starter's env block supplies
   SPRING_DATASOURCE_* and nothing else.

Demonstrated by hiding .env and running the tests as a runner would see them:

  without SPRING_DATASOURCE_*:
    Tests run: 7  CustomerServiceTest   PASS
    ... Unable to obtain connection from database:
        FATAL: password authentication failed for user "crm_app"

  with SPRING_DATASOURCE_* set:
    Caused by: java.lang.IllegalArgumentException:
      Could not resolve placeholder 'JWT_SECRET' in value "${JWT_SECRET}"

Three findings from that pair.

Environment variables outrank application.yml. Setting SPRING_DATASOURCE_URL
pushed the build past the datasource entirely; the ${CRM_DB_URL:...} placeholder
in the yml was never evaluated.

Bean creation order decides which missing value you see. entityManagerFactory
depends on flywayInitializer, so the datasource fails first and masks the JWT
placeholder. Two missing values, one visible at a time.

7 of 26 tests pass without any of this. CustomerServiceTest uses a Mockito mock
and constructs the service directly, so it loads no Spring context. The other
19 need one.

Also incidental: with CRM_DB_URL unset the app fell back to its default,
localhost:5432, which on this machine is an unrelated capstone Postgres. And the
unresolved password reached the driver as the literal string ${CRM_APP_PASSWORD}
-- the same pass-through seen in Lab 42 with ${CRM_DB_HOST}.

Resolved by adding JWT_SECRET as a repository secret and referencing it as
${{ secrets.JWT_SECRET }} in the verify job env. Name in Git, value not.

=== Schema portability fix ===

CustomerRepositoryIT line 110 issued raw SQL against crm_app.customer. That
schema exists only from the Lab 37 DDL, which also set the role's search_path. A
fresh CI Postgres has neither.

  - "UPDATE crm_app.customer SET status = 'CLOSED', version = version + 1 "
  + "UPDATE customer SET status = 'CLOSED', version = version + 1 "

Flyway migrations create tables unqualified, the JPA entity maps unqualified, so
everything resolves through search_path and nothing has to agree on a schema
name. examples/lab41-crm is unchanged.

because failure detail costs bytes. That is what if: always() buys: a red build
nobody has to re-run in order to diagnose.

at the test phase and package never spent its 2m39s.
