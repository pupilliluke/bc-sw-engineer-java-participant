# Lab 37 — CRM Entities

## Step 1 — Entities

`customer` and `account`. address is not needed for the customer and
account design this exercise covers, the CRM UI from labs 34 to 36 shows
name, email and status and never a postal address, so it stays out until
the lab asks for it. the lab overview also adds a status history table,
append-only, which is a second reason not to widen the design here.

## Step 2 — Attributes

Customer: customer_id, full_name, status, created_at. Account:
account_id, customer_id, account_number, type.

| Table | Column | Note |
| --- | --- | --- |
| customer | customer_id | business key, CUS-1001 form, stable across the app |
| customer | full_name | one field, the UI and the API have carried fullName since lab 34 |
| customer | status | PROSPECT, ACTIVE, SUSPENDED, CLOSED |
| customer | created_at | timestamptz, UTC, set by the database |
| account | account_id | surrogate, generated by the database |
| account | customer_id | FK to the owning customer |
| account | account_number | the number a person reads out, unique |
| account | account_type | CHECKING, SAVINGS or similar, constrained later |

email is in the spring api and the UI but not in the deck's attribute
list for this exercise, so it is a column the lab can add rather than
something this sketch invents.

## Step 3 — Fixtures

Amina `CUS-1001`, Ravi `CUS-1002`. Amina is ACTIVE and owns an account,
Ravi is PROSPECT with zero accounts, so the seed covers both sides of the
1:N, a parent with a child and a parent without one.
