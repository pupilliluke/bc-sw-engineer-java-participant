# Lab 39 — Entity Mapping

## Reference

the deck's reference mapping is `@Id private String customerId; //
customer_id`, which assumes customer_id holds `CUS-1001`. the lab 37
schema this lab maps does not work that way, customer_id is `BIGINT
GENERATED BY DEFAULT AS IDENTITY` and `CUS-1001` lives in `public_id
VARCHAR(36)`. so the id split I have been carrying since lab 37 lands
here as two fields, not one.

| Column | Type in the DDL | Java field / annotation |
| --- | --- | --- |
| customer_id | BIGINT identity, PK | `@Id @GeneratedValue(strategy = IDENTITY) @Column(name = "customer_id") private Long customerId;` |
| public_id | VARCHAR(36) NOT NULL UNIQUE | `@Column(name = "public_id", nullable = false, length = 36, updatable = false) private String publicId;` |
| full_name | VARCHAR(150) NOT NULL | `@Column(name = "full_name", nullable = false, length = 150) private String fullName;` |
| email_normalized | VARCHAR(254) NOT NULL UNIQUE | `@Column(name = "email_normalized", nullable = false, unique = true, length = 254) private String emailNormalized;` |
| phone | VARCHAR(30) NULL | `@Column(name = "phone", length = 30) private String phone;` |
| status | VARCHAR(20) NOT NULL, CHECK of four | `@Column(name = "status", nullable = false, length = 20) private String status;` |
| version_no | INTEGER NOT NULL DEFAULT 0 | `@Version @Column(name = "version_no") private int versionNo;` |
| created_at | TIMESTAMPTZ NOT NULL | `@Column(name = "created_at", nullable = false, updatable = false) private Instant createdAt;` |
| updated_at | TIMESTAMPTZ NOT NULL | `@Column(name = "updated_at", nullable = false) private Instant updatedAt;` |

`Instant` for the two timestamps rather than the `LocalDateTime` the
deck's mapping slide uses in its example. the columns are TIMESTAMPTZ,
they carry an instant in time, and LocalDateTime has no zone to carry it
with, so that pairing loses the thing the column type was chosen for.

`version_no` is already in the lab 37 DDL, so `@Version` is a field to
map rather than a column to add. the exercise's troubleshooting row says
plan the optimistic lock field now, and the planning was done two labs
ago.

status stays a String here. an enum would be the four CHECK values and
would read better, but the CHECK is the thing actually enforcing the set
and an enum mapping is a decision about `@Enumerated` ordinal against
string that the lab can make with the entity in front of it.

## Step 2 — Account

| Column | Type in the DDL | Java field / annotation |
| --- | --- | --- |
| account_id | BIGINT identity, PK | `@Id @GeneratedValue(strategy = IDENTITY) private Long accountId;` |
| account_number | VARCHAR(34) NOT NULL UNIQUE | `@Column(name = "account_number", nullable = false, unique = true, length = 34) private String accountNumber;` |
| customer_id | BIGINT NOT NULL, FK | `@ManyToOne(fetch = LAZY) @JoinColumn(name = "customer_id", nullable = false) private CustomerEntity customer;` |
| account_type | VARCHAR(20) NOT NULL, CHECK | `@Column(name = "account_type", nullable = false, length = 20) private String accountType;` |
| status | VARCHAR(20) NOT NULL, CHECK | `@Column(name = "status", nullable = false, length = 20) private String status;` |
| balance | NUMERIC(19,2) NOT NULL | `@Column(name = "balance", nullable = false, precision = 19, scale = 2) private BigDecimal balance;` |
| currency | CHAR(3) NOT NULL | `@Column(name = "currency", nullable = false, length = 3) private String currency;` |
| opened_at | TIMESTAMPTZ NOT NULL | `@Column(name = "opened_at", nullable = false, updatable = false) private Instant openedAt;` |

BigDecimal for balance, not double. NUMERIC(19,2) is exact decimal and
double is binary floating point, so the column can hold 2500.00 and a
double cannot promise to give it back. lab 37's verify script asserts
this on the database side already, the row headed money type is exact,
not binary float, reading numeric_precision 19 and numeric_scale 2. the
Java side has to agree or the exactness stops at the driver.

the exercise sketches account as `Long id, String customerId`, a plain
foreign key field. `@ManyToOne` to the entity is the mapping the deck
builds toward and it is what makes the join the one lab 38 measured,
`ix_account_customer` on account (customer_id), reachable from JPQL. LAZY
so loading a customer does not drag every account behind it. the
relationship is mapped one way only for now, account to customer, since
nothing in the lab needs to walk a customer to their accounts yet and an
unneeded `@OneToMany` is a collection Hibernate has to manage.

## Step 3 — Naming

snake_case columns, camelCase fields, and every column named explicitly
in `@Column(name = ...)`.

the deck's mapping example writes the name out, `@Column(name =
"customer_name", nullable = false, length = 100)`, and that is the side
to err on here. these column names are the contract lab 37 wrote and lab
38 tuned, `email_normalized` and `public_id` and `version_no` are not
incidental spellings. writing them in the annotation puts the binding in
the file where a rename would show up in the diff, instead of leaving it
to a convention that could be reconfigured somewhere else in the project.

it is the same reasoning as naming the constraints in lab 37 rather than
letting PostgreSQL generate names. a name I wrote is a name I can search
for when something breaks.

the length, nullable and updatable attributes come across from the DDL
too, so the entity states the same rules the table enforces. Flyway owns
the schema and Hibernate validates against it, per the exercise's
troubleshooting row, so a mismatch between the two is a startup failure
rather than a silent divergence.

## Step 4 — Fixture

one CustomerEntity instance, Amina:

| Field | Value |
| --- | --- |
| customerId | a BIGINT the database assigned, not written by hand |
| publicId | `CUS-1001` |
| fullName | `Amina Khan` |
| emailNormalized | `amina@example.com` |
| phone | `+1-555-0101` |
| status | `ACTIVE` |
| versionNo | 0 on insert, 1 after the first update |
| createdAt | an Instant the database set |

her one AccountEntity is `ACCT-1001-01`, CHECKING, balance
`BigDecimal("2500.00")`, CAD, with its `customer` reference pointing back
at her row. Ravi `CUS-1002` is PROSPECT with an empty account side, which
is the case that catches a mapping that assumed every customer has one.

the thing to hold onto is that customerId is not something the code
supplies. the entity is constructed with publicId and the rest, the
database fills the identity, and any code that looks a customer up by
`CUS-1001` is querying publicId. that is the same rule the lab 37 seed
followed when it looked its parent up by public_id instead of hardcoding
a surrogate.
