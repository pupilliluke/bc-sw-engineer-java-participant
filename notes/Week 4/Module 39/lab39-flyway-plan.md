# Lab 39 — Flyway Plan

## Step 1 — Version file

`V1__crm_schema.sql`, under `src/main/resources/db/migration`.

the name is the contract. `V` for a versioned migration, `1` the
version, two underscores separating version from description, and the
description in the rest. Flyway records the version and a checksum of
the file in its own table, so the name is what it keys on and the
content is what it hashes.

## Step 2 — Content

the lab 37 DDL, unchanged, plus the index lab 38 earned.

| From | What goes in V1 |
| --- | --- |
| lab 37 step 5 | `customer`, with public_id, email_normalized, status, version_no, created_at, updated_at |
| lab 37 step 6 | `account`, NUMERIC(19,2) balance, FK to customer |
| lab 37 steps 7-8 | `address`, `customer_status_history` |
| lab 37 all | the 17 named constraints, PK, UK, FK and CHECK |
| lab 37 step 9 | `ix_account_customer`, `ix_address_customer`, `ix_history_customer_time` |
| lab 38 step 7 | `ix_customer_status_created` on (status, created_at DESC, customer_id DESC) |

the last row is the one worth stating out loud. lab 38 measured that
index at 1,006 buffers down to 23 on the ACTIVE list and re-earned it in
the step 12 challenge cycle. it exists in my lab 38 database because a
script created it interactively. if V1 does not carry it, then the
schema Flyway builds on a fresh machine is missing the only index this
CRM has evidence for, and the measurement stops being reproducible. the
migration is the source of truth, so anything not in it did not really
happen.

`version_no` is the same case in miniature. it is in the lab 37 DDL
already, which is why `@Version` in lab39-todos.md is a field to map
rather than a column to add.

PostgreSQL syntax, since Flyway runs this against PostgreSQL:
`BIGINT GENERATED BY DEFAULT AS IDENTITY`, `NUMERIC(19,2)`,
`TIMESTAMPTZ`, `VARCHAR`. no `NUMBER`, no `VARCHAR2`, no sequence plus
trigger for the id. the identity line is the one piece that ports as
written, which is the same note lab 37 made.

the seed is not in V1. Amina and Ravi are fixtures, not schema, and a
migration that inserts them makes every environment carry test data.
they belong in a separate seed script or a test fixture, the way lab 37
kept `03_seed.sql` apart from `02_schema.sql`.

## Step 3 — Why Flyway

schema changes are versioned and repeatable across every machine, so the
database a teammate gets is the database I have, arrived at by the same
steps in the same order.

the part that matters beyond repeatability is that it is forward-only
and recorded. Flyway keeps a table of what ran and when, so the schema's
state is a fact to query rather than something to infer, and a migration
that already ran is never run again.

## Step 4 — Anti-pattern

`spring.jpa.hibernate.ddl-auto: create-drop` on a shared environment.
`validate` is the setting, per the deck's config slide.

create-drop drops every table on shutdown. against this database that is
50,002 customers, 25,001 accounts and both fixtures, gone because an
application stopped. `update` is the subtler one and the reason the
Debug prompt asks about mixing it with Flyway: it never drops anything,
so it looks safe, but it makes Hibernate a second thing with an opinion
about the schema. Flyway applies V1, Hibernate then adds whatever it
thinks is missing, and now the schema is the sum of two mechanisms and
matches no file anyone can read. one owner, and it is Flyway.

`validate` is the setting that makes the split enforceable. Hibernate
compares the entities against what is actually there and refuses to
start on a mismatch, so a field renamed without a migration is a startup
failure rather than a query that fails in production later.

editing V1 after it has been applied: write `V2__whatever.sql`. Flyway
stores a checksum of every applied migration, so an edited V1 fails
validation on the next start, and the temptation is `flyway repair`,
which just rewrites the checksum to match the edit. that hides the
change rather than applying it, and every database where V1 already ran
still has the old schema while the file claims otherwise. repair is for
a failed migration entry, not for making an edit go quiet. once V1 has
run anywhere it is history, and history gets appended to.
