# Lab 38 — Access Patterns

## Step 1 — Patterns

lookup by `public_id` (`CUS-1001`), lookup by email, filter by status,
filter by `created_at` range, and accounts by `customer_id`.

| Pattern | Table.column | Operator | Where it comes from |
| --- | --- | --- | --- |
| open one customer | customer.public_id | equality | the id in the CRM url, `CUS-1001` |
| find by email | customer.email_normalized | equality | login and the find-a-customer box |
| list by status | customer.status | equality | the ACTIVE / PROSPECT filter the UI has had since lab 34 |
| date window | customer.created_at | range | reports over a from/to pair |
| a customer's accounts | account.customer_id | join | the detail screen loads the accounts under the customer |

the deck writes the hot path as `WHERE customer_id = 'CUS-1001'`, but the
lab 37 schema I built has `customer_id BIGINT GENERATED BY DEFAULT AS
IDENTITY` and puts `CUS-1001` in `public_id VARCHAR(36)`. so the column
the app filters on for that pattern is public_id, and customer_id is the
join key between the two tables. the shape of the pattern is the same
either way, one exact value, one row.

three of these already have an index out of lab 37 step 9,
`uk_customer_public`, `uk_customer_email` and `ix_account_customer`.
status and created_at have nothing, which is where this module goes next.

equality and range are worth separating because the index behaves
differently. equality walks down to one point, range finds the boundary
and then reads forward, and in a composite index that means the range
column has to be last.

## Step 2 — Hot path

single-customer lookup is the hottest path, `public_id` equality on
customer. it is the query every CRM screen calls first, the detail view
and the edit form both start there, and the accounts join in the table
above hangs off the row it returns. unique index, one row, so it is also
the cheapest of the five once it is indexed.

status is the opposite case. it is equality too but only four values
exist across the whole table, so a filter on ACTIVE matches a large
fraction of the rows and an index on it alone may not earn its keep.
that is the write cost question, every index is maintained on insert and
update, so an index that a query does not really use is paid for and not
collected.

## Step 3 — Anti-pattern

`SELECT * FROM customer;` with no WHERE clause on a big table, avoid it
in application code. it reads every row and every column including ones
the screen never renders, and no index can help a query that asked for
everything.
