# Lab 37 design decisions

PostgreSQL CRM schema for Northstar, `examples/lab37-crm`. Tables before ORM:
Lab 38 tunes queries on this schema and Lab 39 maps it with JPA, so the column
names and constraint names here are the contract both inherit.

## Entities and cardinalities

```text
Customer 1 ---- 0..* Account
Customer 1 ---- 0..* Address
Customer 1 ---- 0..* StatusHistory
```

Diagram in `er-diagram.md`. The optional many is the design decision, not a
detail: Ravi Singh is a PROSPECT with zero accounts, and a mandatory account
would make him unrepresentable.

## Identifiers

| Column | Kind | Rule |
| --- | --- | --- |
| `customer_id` | identity surrogate | PK and FK target, internal, never leaves the database |
| `public_id` | business key | `CUS-1001`, immutable, what the API and UI carry |
| `email_normalized` | unique lookup | lowercased, unique, but changeable — never a key |
| `account_number` | business key | `ACCT-1001-01`, unique |

Splitting the surrogate from the public id means a customer can be re-keyed
internally without changing what the outside world quotes, and joins stay on a
BIGINT rather than a string.

`ck_customer_email_lower` enforces the "normalized" part of
`email_normalized`. Without it the column name is a promise the database does
not keep, and `Amina@example.com` would sit beside `amina@example.com` with the
unique constraint satisfied.

## Types

| Choice | Instead of | Why |
| --- | --- | --- |
| `NUMERIC(19,2)` for balance | `double precision` / `FLOAT` | binary floating point cannot represent 0.10 exactly; money must be a decimal type |
| `TIMESTAMPTZ` | `TIMESTAMP` | stores an absolute instant, UTC; a naive timestamp means nothing without knowing the writer's zone |
| `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `SERIAL` | standard SQL identity, no separate sequence to grant on; `SERIAL` is a legacy PostgreSQL shorthand |
| `VARCHAR(n)` with explicit lengths | `TEXT` everywhere | same storage in PostgreSQL, but the length documents the intent to the next reader and to the UI |
| `CHAR(3)` currency, `CHAR(2)` country | `VARCHAR` | genuinely fixed-width codes, ISO 4217 and ISO 3166-1 alpha-2 |

## Delete rules

| Child | ON DELETE | Why |
| --- | --- | --- |
| `account` | RESTRICT | a financial record; the delete should fail and force a decision about the balance |
| `address` | CASCADE | describes only its customer |
| `customer_status_history` | CASCADE | same lifetime as the customer |

RESTRICT is also PostgreSQL's behaviour when no action is named, so writing it
states the intent rather than changing it. Negative test 5 in `04_verify.sql`
proves it by deleting Amina and expecting SQLSTATE 23503.

## History is append-only

`customer_status_history` is inserted, never updated. An overwritten status
loses the transition, which is the only record of who changed what and why —
`changed_by`, `reason`, and `correlation_id` (`lab-request-001`, the same
correlation id the Spring and React labs have carried since Lab 25). The
`ck_hist_transition` CHECK rejects a row whose old and new status are equal,
using `IS DISTINCT FROM` so that a NULL old status (the first row for a
customer) still passes.

## Constraints are named

Every PK, UK, FK and CHECK has an explicit name (`pk_customer`,
`uk_customer_email`, `fk_account_customer`, `ck_customer_status`). The name is
what appears in the error, so a failing insert says which rule it broke rather
than pointing at a generated `customer_status_check`. Lab 39's JPA mapping and
any application error handling both key off these names.

## Indexes

`ix_account_customer`, `ix_address_customer`, and
`ix_history_customer_time (customer_id, changed_at)`.

PostgreSQL creates an index for a PRIMARY KEY and for UNIQUE automatically, but
**not** for a foreign key. An unindexed FK means every parent delete or update
scans the child table, and the timeline query for one customer's history sorts
without help. `public_id` and `email_normalized` are already unique, so no
extra index is added over them.

## Least privilege

The container's bootstrap superuser is `crm_admin`, and the application role
`crm_app` is created separately by `01_create_user.sql` with
`NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOREPLICATION`. It owns the
`crm_app` schema and has no rights on `public`. Evidence of the flags is the
last query in that script.

This is a deliberate departure from the GUIDE's `docker run`, which sets
`POSTGRES_USER=crm_app` — that makes `crm_app` the bootstrap superuser, which
is the opposite of what step 4 asks for. Two roles, one privileged and one not,
is the only way both steps can be true at once.

## Secrets

Passwords live in `.env`, which is gitignored; `.env.example` carries the shape
with placeholder values. `01_create_user.sql` takes the application password as
a psql variable (`-v crm_app_password=...`) so it is not written into the SQL
file. All of these are lab-only credentials.

## Oracle dialect in the GUIDE

The GUIDE is a PostgreSQL lab with Oracle text left in it. The translations
used here:

| GUIDE (Oracle) | Used here (PostgreSQL) |
| --- | --- |
| `DROP TABLE x CASCADE CONSTRAINTS PURGE` | `DROP TABLE IF EXISTS x CASCADE` — no recycle bin exists to purge |
| ORA-02290 check constraint violated | SQLSTATE 23514 `check_violation` |
| ORA-00001 unique constraint violated | SQLSTATE 23505 `unique_violation` |
| ORA-02291 integrity constraint / parent key not found | SQLSTATE 23503 `foreign_key_violation` |
| ORA-01400 cannot insert NULL | SQLSTATE 23502 `not_null_violation` |
| ORA-00955 name is already used | SQLSTATE 42P07 `duplicate_table` |
| ORA-01017 invalid credential | SQLSTATE 28P01 `invalid_password` |
| `QUOTA ON USERS` tablespace | no per-user quota; PostgreSQL uses tablespaces without quotas |
| `NUMBER(p,s)`, `VARCHAR2` | `NUMERIC(p,s)`, `VARCHAR` |

The five-digit SQLSTATE codes are standard SQL and are what an application
catches — that is how a duplicate email becomes a 409 rather than a 500.

## What is deliberately not here

No Kafka outbox table (Modules 30–31 own that), no JPA annotations or Flyway
migrations (Lab 39), and no query tuning or EXPLAIN work (Lab 38).
