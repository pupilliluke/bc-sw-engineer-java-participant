8, THE RULE ORDER

Not in the guide. Reordered CustomerValidator.validateNew to look up the email
before the id.

  mvn -B test

[ERROR] Tests run: 98, Failures: 1, Errors: 1, Skipped: 0

Both orders reject a duplicate id with the same 409 and store the same
nothing, so all eighty-three tests carried forward from lab 17 stayed green.
Two of the new ones failed:

org.mockito.exceptions.verification.NeverWantedButInvoked:
repository.existsByEmail(<any string>);
Never wanted here:
-> at CustomerServiceMockitoTest.aDuplicateIdIsRejectedBeforeTheEmailIsLookedUp(CustomerServiceMockitoTest.java:188)
But invoked here:
-> at CustomerValidator.validateNew(CustomerValidator.java:59) with arguments: [ravi.singh@example.com]

org.mockito.exceptions.misusing.UnnecessaryStubbingException:
  1. -> at CustomerServiceMockitoTest.aDuplicateEmailIsA409AndNeverSaves(CustomerServiceMockitoTest.java:194)

The second one is the same reorder seen from the other side, the existsById
stub is now dead because the email check throws first.

This is what the interaction tests add. A rule that runs in the wrong order
throws the same exception, stores the same nothing and covers the same lines,
so neither a state assertion nor the coverage gate can see it. It matters in
production too: an id check that happens after an email check sends the
customer's address to the store on a request that was already invalid.
Restored, and the order is asserted rather than assumed from now on.
