3, REPEAT CREATE CUS-1001

  POST CUS-1001  {"error":"Duplicate customerId: CUS-1001"} HTTP 409

  2026-08-05 17:08:40,778 WARN  [http-nio-8080-exec-7] c.n.crm.service.CustomerService corr=lab-request-001 cust=CUS-1001 op=customer.create - Create rejected reason=duplicate

  GET CUS-1001  {"id":"CUS-1001","name":"Amina Khan","email":"amina.khan@example.com","status":"ACTIVE"} HTTP 200

Duplicate rather than overwrite. The repository's save is a plain map put and
would overwrite, but CustomerService.create checks findById first and throws
DuplicateCustomerException, which is lab 19 behavior carried forward. The
record still reads Amina Khan after the rejection.

The store is the singleton's ConcurrentHashMap, so the seeded CUS-1001 and
CUS-1002 outlive every request and the rule applies from the first POST
onwards. This is why CustomerServiceTest creates CUS-2001 and
CustomerServiceSpringTest creates CUS-2202 instead of the guide's Amina.
