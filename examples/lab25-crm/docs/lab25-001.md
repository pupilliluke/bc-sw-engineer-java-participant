# Lab 25 AI review log (`lab25-001`)

repository/InMemoryCustomerRepository.java, service/CustomerService.java,

## Accepted after review

- Service depends on the CustomerRepository interface, never on
  InMemoryCustomerRepository. The concrete class is only named in the tests,
  where it is the test double.
- Constructor injection with a final field on CustomerService.
- existsById check before save, so the map cannot silently overwrite CUS-1001.
- findAll returning a new ArrayList rather than the live values() view.
- The transition table carried from lab 15 rather than a fresh one. Same allowed
  pairs, same CLOSED-is-terminal and same-status-rejected consequences.

## Rejected

- ResponseEntity returned from CustomerService.get. Experiment 5 in
  notes/screenshots/lab-25/03-failure-experiments.txt shows the compile error it
  produces in CustomerController. HTTP types stay in the controller.
- @Autowired fields in place of the constructor. A missing repository has to
  fail at startup.
- JPA annotations on Customer and on the repository interface. That is Lab 39
  and there is no PostgreSQL here yet.
- A CustomerStatus enum to back the transition table. Lab 15 had one; this
  build's model carries status as a String and the starter says the enum is not
  required, so the table is String-keyed and the model is untouched.
- Reading the status straight off the request and calling setStatus without
  checking the table. That is what lab 12's updateStatus did and it is the
  reason experiment 2 exists.

## JPA readiness

CustomerRepository is the seam. Later it becomes
`extends JpaRepository<Customer, String>`, which already supplies save,
findById, findAll and existsById under the same names and shapes. Customer gains
@Entity and @Id. CustomerService keeps the same four calls, and
CustomerController keeps POST /api/customers and GET /api/customers/{id}
unchanged, so no route moves when persistence swaps.
